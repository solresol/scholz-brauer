## All 16 optimal chains are one family

The 18 October records called chains 1-8 the transposes of chains 9-16. That
was wrong. The reversed path counts of chain 9 take only 25 distinct values
for its 28 vertices, so they are not a chain.

Every optimal chain is a run-generalised Clift graph G(a,s,b,c):
- R0 = 1 and Ri = 2R(i-1) up to "2" = Ra;
- s doublings from "2" to "4";
- "5" = "4" + 1, "7" = "5" + "2", "8" = 2*"4", "15" = "8" + "7", F0 = "15" + "8";
- b doublings to Fb, then "28" = Fb + "5" and G0 = "28" + Fb;
- c doublings to Gc, then "58" = Gc + "7" and n = "58" + Gc.

There are three chord variants:
- vX: "16" = 2*"8" and F0 = "16" + "7";
- vY: "46" = 2*Fb and G0 = "46" + "5";
- vZ: "102" = 2*Gc and n = "102" + "7".

Chains 1-8 are G(4,10,0,4) and chains 9-16 are G(5,1,9,3), with variant
(vX,vY,vZ) = binary(k-1) and binary(k-9) respectively. Every chain in the data
file was checked value by value, with the unique parent pair of every step.

The nine-component loss decomposition of chain 9 holds unchanged for every
variant and every s (class v then has s differences). The only changes are
which critical paths exist and their cap constraints:
- vX leaves only 4-8-16-23, so there is no critical path through 4-5-7 and no
  anchor A1;
- vY leaves only Fb-46-51;
- vZ leaves only Gc-102-n.

With b = 0, vX = 0 and vY = 0 (chains 1 and 2) there are also candidate paths
4-5-28-51. Under vX the vertex 8 doubles, so it lies on every critical path,
and under vY so does 23. They are impossible: after either copy of 4->8, the zero-shift
routes 8-15-23-28 and 8-23-28 would give two paths of equal weight. The
detour program reports exactly these candidates as rejected.

## Searches

- **Loss search** (`clift5784689_loss_search.cpp`, options `var=` and `s=`).
  This is the chain-9 engine with the variant critical paths added. With
  s = 1 and no variant it reproduces every earlier node count exactly
  (G(1,0,0), G(2,1,1), G(3,3,1), G(1,9,0), both anchors). Chains 13-16 ran on
  the Mac (3 workers, Apple clang 21) under `clift5784689_parallel.py`, with
  source sha256 2bf90421….
- **Detour search** (`clift5784689_detour_search.cpp`, unchanged, sha256
  9267ff12…). This is the independently written per-critical-path program,
  run on each chain's explicit parent list (`--pairs`). Each P* uses six split
  jobs, as in the chain-9 campaign. Chains 13-16 ran on raksasa (g++ 15.2).

## Validation (chains 13-16 report)

- **Loss decomposition and anchors.** 2,000 random critical-path-saturated
  labellings of random small G(a,s,b,c), over every variant and family, with
  s up to 3. The decomposition matches explicit path enumeration, and the
  dynamic-programming atoms agree.
- **Caps soundness.** The caps test accepts 3,168 relaxed queries from 1,056
  non-degenerate labellings. It also accepts 6,400 queries (400 per chain)
  from saturated labellings of every one of the 16 chain graphs.
- **Leaf checks.** All 48 configurations of each of G(1,0,0), G(2,0,0),
  G(1,1,0), G(1,0,1) and G(2,1,1) fail the explicit cost-(n-1) system under all
  eight variants.
- **Positive control.** With constraint groups dropped, over variants and
  s = 2, the pruned search returns exactly the leaf-passing configurations:
  554 in 126 cases.
- **Detour coverage.** Every critical path has its complete set of six split
  jobs, all clean ("no labelling", no leaf, no truncation).

## Failed and bounded approaches

- Raksasa was oversubscribed: another user's job (tw41) and a classifier left
  each process about 40% of a core. Loss-search jobs then hit the 300 s
  timeout and were re-split more often, which wasted work. The raksasa runs
  for chains 5-8 use a 600 s timeout.
- The detour program is about 5 times slower per critical path on chains 1-3
  (the 10-doubling run, b = 0) than on chains 9-16: 35-55 minutes per job.
