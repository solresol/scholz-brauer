# All 16 optimal chains of 5,784,689 have no labelling with n-1 doublings

19 October 2026, Monday, Australia/Sydney (AEDT). Milestone 3. This note
covers chains 1-8 and 10-16. Each block of chains has its own evidence file.
Chain 9 is in `2026-10-19-clift5784689-chain9.md`.

## Result

**For every one of Clift's 16 optimal 27-step chains for 5,784,689, no Clift
labelling has cost n-1 = 5,784,688.** Each chain is excluded by two
independently written complete searches. So no optimal chain for 5,784,689
gives l(2^5784689 - 1) <= 5,784,688 + 27 = 5,784,715 through a Clift
labelling.

These are computational exclusions, not Lean theorems. They say nothing about
other addition chains for 2^5784689 - 1, or about chains for 5,784,689 that
are not optimal. They say nothing about Scholz-Brauer at 5,784,689. No
novelty claim is made.

## All 16 optimal chains are one family

The 18 October records called chains 1-8 the transposes of chains 9-16. That
was wrong. The reversed path counts of chain 9 take only 25 distinct values
for its 28 vertices, so they are not a chain.

Every optimal chain is a run-generalised Clift graph G(a,s,b,c):
- R0 = 1 and Ri = 2R(i-1) up to "2" = Ra;
- s doublings from "2" to "4";
- "5" = "4" + 1, "7" = "5" + "2", "8" = 2*"4", "15" = "8" + "7", F0 = "15" + "8";
- b doublings to Fb, then "28" = Fb + "5" and G0 = "28" + Fb;
- c doublings to Gc, then "58" = Gc + "7" and n = "58" + Gc.

There are three chord variants:
- vX: "16" = 2*"8" and F0 = "16" + "7";
- vY: "46" = 2*Fb and G0 = "46" + "5";
- vZ: "102" = 2*Gc and n = "102" + "7".

Chains 1-8 are G(4,10,0,4) and chains 9-16 are G(5,1,9,3), with variant
(vX,vY,vZ) = binary(k-1) and binary(k-9) respectively. Every chain in the data
file was checked value by value, with the unique parent pair of every step.

The nine-component loss decomposition of chain 9 holds unchanged for every
variant and every s (class v then has s differences). The only changes are
which critical paths exist and their cap constraints:
- vX leaves only 4-8-16-23, so there is no critical path through 4-5-7 and no
  anchor A1;
- vY leaves only Fb-46-51;
- vZ leaves only Gc-102-n.

With b = 0, vX = 0 and vY = 0 (chains 1 and 2) there are also candidate paths
4-5-28-51. Under vX the vertex 8 doubles, so it lies on every critical path,
and under vY so does 23. They are impossible: after either copy of 4->8, the zero-shift
routes 8-15-23-28 and 8-23-28 would give two paths of equal weight. The
detour program reports exactly these candidates as rejected.

## Searches

- **Loss search** (`clift5784689_loss_search.cpp`, options `var=`, `s=` and
  `halve=all`). This is the chain-9 engine with the variant critical paths
  added. With s = 1, no variant and no `halve=all`, it reproduces every earlier
  node count exactly (G(1,0,0), G(2,1,1), G(3,3,1), G(1,9,0), both anchors).
  All runs used the Mac (3 workers, Apple clang 21) under
  `clift5784689_parallel.py`. Chains 13-16, 12 and 11 (anchor t) used source
  sha256 2bf90421… without `halve=all`. The other runs used source a67cbc3f…
  with `halve=all`. The current source has the same default behaviour, which
  the checker confirms by replaying root job lists and sampled jobs.
- **Detour search** (`clift5784689_detour_search.cpp`, unchanged, sha256
  9267ff12…). This is the independently written per-critical-path program,
  run on each chain's explicit parent list (`--pairs`). Each P* uses six split
  jobs, as in the chain-9 campaign; the candidates 4-5-28-51 of chains 1 and 2
  are rejected outright. Chains 1 and 10-16 ran on raksasa (g++ 15.2), and
  chains 2-8 on the Mac.

## Halving for every class (`halve=all`)

The halving test of the chain-9 search applies to every class, not only F
and G. A component that contains class k is a disjoint union of pairs
{y, y + d} for each difference d of class k. The components without class k
form a set E_k. So every residue class mod d of [0, n) has an even number of
elements outside E_k, and [0, n) has at most |E_k| runs of odd length in
steps of d. A difference whose class is still a lazy block must pass the
test for at least one class of the block.

|E_k| is the sum of 2^(number of differences) over the components without
class k. For chains 1-8, |E_U| = 97 and |E_V| = 1,137, which is tiny against
n = 5,784,689. Without this test, the ten V differences of chains 1-8 are
almost unconstrained: the chain-8 run below grew past 71M nodes. With it,
chain 8 takes 635,527 nodes and 39 s.

For chains 9-16 the sets are larger (|E_U| = 16,401, |E_V| = 540,721). The
option removes only about 25% of the nodes there, but the run time falls much
more, because no job then exceeds the 300 s limit and needs re-splitting. Chain
10 took 7 minutes with the option, against 90 minutes for chain 12 without it.

The option is off by default, so the chain-9 and chains 13-16 evidence
replays unchanged. It only prunes: without caps pruning it returns the same
configurations as before, which is checked in the report.

## Validation

### Chains 13-16 report

- **Loss decomposition and anchors.** 2,000 random critical-path-saturated
  labellings of random small G(a,s,b,c), over every variant and family, with
  s up to 3. The decomposition matches explicit path enumeration, and the
  dynamic-programming atoms agree.
- **Caps soundness.** The caps test accepts 3,168 relaxed queries from 1,056
  non-degenerate labellings. It also accepts 6,400 queries (400 per chain)
  from saturated labellings of every one of the 16 chain graphs.
- **Leaf checks.** All 48 configurations of each of G(1,0,0), G(2,0,0),
  G(1,1,0), G(1,0,1) and G(2,1,1) fail the explicit cost-(n-1) system under all
  eight variants.
- **Positive control.** With constraint groups dropped, over variants and
  s = 2, the pruned search returns exactly the leaf-passing configurations:
  554 in 126 cases.
- **Detour coverage.** Every critical path has its complete set of six split
  jobs, all clean ("no labelling", no leaf, no truncation).

### Chains 1-8 and 10-12 report

`results/2026-10-19-clift5784689-chains1-12.json` (678 s) repeats every test
above with a fresh seed: 2,000 random saturated labellings; 3,168 relaxed
caps queries; 6,400 chain-graph caps queries; leaf checks. It adds:
- **Reference for s > 1.** For G(1,0,0) with s = 2 and 3, and for G(2,0,0)
  with s = 2, both anchors, the C++ search without caps pruning returns exactly
  the Python reference's configurations: 48 per graph. All fail the explicit
  cost-(n-1) system under all eight variants.
- **Positive control with `halve=all`.** For the same 126 cases, with and
  without the option, the pruned search returns exactly the 554 leaf-passing
  configurations.
- **Halving only prunes.** On 22 small graphs (s up to 3, several variants,
  both anchors), the search without caps pruning returns the same 560
  configurations with and without `halve=all`. The option removes 5-35% of
  the nodes there.
- **Run options.** Every run directory records its options. They agree with
  the run logs and the chain's variant and s, and the checker replays every
  root job list and two sampled jobs per run with them.
- **Detour coverage.** For chains 1-8 and 10-12, every critical path has its
  complete set of six split jobs, all clean. The three candidates 4-5-28-51
  of chains 1 and 2 are rejected outright.

## Failed and bounded approaches

- **Chains 1-8 without `halve=all`.** On raksasa, the chain-8 loss search
  (anchor t, 300 s timeout) reached 70,990,555 nodes in 2,086,745 job records
  after 5 hours, with 9,426,350 jobs pending and the queue still growing. The
  ten V differences had no halving constraint. Someone other than this
  session stopped that run with SIGSTOP at 19:31, and it was not resumed. Its
  processes are obsolete, and removing them is left to the user.
- **Raksasa contention.** The user's `tw41` job and another user's classifier
  left each process about 40% of a core. Loss-search jobs then hit the timeout
  and were re-split more often, which wasted work. Every loss search in the
  evidence therefore ran on the Mac.
- **Detour cost.** The detour program is about 5 times slower per critical
  path on chains 1-3 (the 10-doubling run, b = 0) than on chains 9-16: up to
  55 minutes per job, 38 CPU-hours for chain 1.
- **A hand-written options file.** Runs started before the driver wrote
  `options.json` had it written by hand. One of them (chain 7) first said
  variant 111 instead of 110. The report's consistency check rejected it,
  and it was corrected from the run log before the evidence was produced.
