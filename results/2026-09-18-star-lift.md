# 2026-09-18 — Friday — checked Brauer lift

## Result and boundary

An explicit addition-chain certificate reaches `2^12509 - 1` in **12,526
additions**. Exact integer replay checks every summand index, strict increase,
endpoint and length. A second check discards the indices and tests each value's
difference from its predecessor for membership among earlier values.

This proves the numerical upper bound `ell(2^12509 - 1) <= 12526` by a checked
witness. It is not a Lean proof, an optimality proof, or a verification of the
Scholz bound at 12509. The literature's `ell(12509)=17` would give target 12525;
the repository currently proves only `14 <= ell(12509) <= 17`. Substituting a
known upper bound for ell(n) on the conjecture's right side does not prove
the conjecture. No novelty is claimed.

## Construction and certificate format

Write `M_a = 2^a - 1`. Given a star step `a -> a+b`, where `b` is already an
exponent in the source chain, append `b` doublings of `M_a`, then add the stored
`M_b`. The endpoint identity is

```
2^b * (2^a - 1) + (2^b - 1) = 2^(a+b) - 1.
```

Every appended value strictly increases because the input exponents, Mersenne
values and their doublings are positive. The stored `M_b` already occurs:
each completed source step stores its Mersenne value. Starting with `M_1=1`,
induction gives a valid star chain. For a source of length `r` ending at `n`,
the doubling counts telescope to `n-1`; there are `r` final additions, giving
**exactly `n-1+r` steps**. This specifies the implementation and next Lean
lemma. The singleton source `[1]` gives the zero-step certificate.

The saved JSON format is `addition-chain-indices-v1`. Starting with `values=[1]`,
pair number `i` (counting from 1) names two indices in `[0,i)`, whose sum is
appended. Indices are zero-based; repeated indices allow doubling. All 12,526
pairs are stored explicitly, without macros or reliance on the generator.
`source_chain` is provenance only. The standalone checker takes the exponent
and expected count separately from the document, so altered declarations
cannot silently weaken the check.

## Reproduction and evidence

From the repository root, with Python **3.9.6**, standard library only:

```sh
python3 scripts/star_lift.py data/12509-star.json results/2026-09-18-12509-star-certificate.json
python3 scripts/check_certificate.py results/2026-09-18-12509-star-certificate.json --exponent 12509 --additions 12526 --require-star
python3 scripts/verify_star_lift.py --output results/2026-09-18-star-lift-checks.json
python3 scripts/check_12509.py
```

The bounded verifier took **0.318886 seconds**. It checked all **842** star
chain prefixes with at most six additions and endpoint at most 32, including
`[1]`; binary-chain lifts for every exponent **1..256**; and the published
12509 input and saved certificate. These are overlapping test families, not
an exhaustive search for minimum lengths. The older checker independently
discovers every valid parent pair for binary lifts with exponents 1..16 and
for the published input. No randomness, seed, timeout or heuristic search
is involved. The saved full certificate is the reproducible checkpoint.

All **23 negative checks** passed: malformed/non-star sources, invalid indices
and counts, false endpoints, a damaged final operation, and attempts to check
the saved certificate with exponent 12508 or count 12525. The certificate
also checks after removing its source-chain provenance field.

An initial negative fixture used `[1,2,3,5,6]` with final parents `3+3` and
incorrectly expected rejection by the star checker. In fact `6=5+1` is also
available. Corrected the fixture to the non-star prefix ending `12,13,24`,
and retained the alternative-decomposition case as a positive regression.
This was a test-design error, not a failed mathematical hypothesis.
