# One exceptional base for Clift's non-Hansen source

6 October 2026, Tuesday, Australia/Sydney (AEDT). Active milestone: 3.
Milestones 1 and 2 were already complete and were not reopened.

## Question and result

For the fixed formal source `[1,2,4,8,9,13,16,29]`, can a shifted-base
construction achieve `29-1+7=35` additions after allowing one base to depart
from the usual Mersenne value? **Yes, for this source.** The exceptional base
is 8161 at source value 9. All other bases remain Mersenne numbers, including
8191 at source value 13. The finite witness and non-Hansen marking obstruction
are now kernel checked. This reproduces and explains a published example;
it is not a new upper bound for 29 or a general extension theorem.

[Clift's primary notes](https://www.additionchains.com/ScholzBrauer.html), live
undated page, accessed 6 October 2026, supply the source and an abbreviated
lift. The source, displayed prefix and last two values were re-read and match
the reconstructed certificate; metadata is in
`data/2026-10-06-non-hansen29-source.json`. No immutable version is supplied by
the page. Larger examples and claims of optimality/priority are not used.

## Explicit hypotheses and exhaustive domain

H0: standard local Mersenne concatenations on this fixed parent graph can
meet the 28-doubling budget. This is **false**. Every source value has exactly
one unordered parent pair. Only the three unequal pairs have a meaningful
orientation choice; all eight assignments have doubling totals
`32,35,33,36,39,42,40,43`. Their minimum allocation has 39 additions, four more
than the target. Lean checks the minimum of the explicitly defined cap
function; the correspondence of that function with all standard graph
orientations is an ordinary finite argument, also checked in Python.
This does not exclude arbitrary constructions outside that scheme.

H1: permitting a single exceptional base, at source value 9, suffices on this
graph while keeping the 28-doubling budget. This is **true on this instance**.
We searched the larger family that allows both bases 9 and 13 to vary, with
bases at 1,2,4,8,16 fixed to their Mersenne values. Write

```
B9  = (255 << a) + (1 << b)
B13 = (B9 << c) + (15 << d)
T   = (65535 << e) + (B13 << f), T = 2^29 - 1.
```

The complete doubling cost is
`max(1,b)+2+max(4,d)+max(8,a)+c+e+f`. All labels are nonnegative integers.
Cost at most 28 implies every label is in `0..28`. The forward enumeration
loops a,b,c,d,e with exact cost/positive-endpoint pruning, then derives f by
integer division and an exact power-of-two test. It examines 67,508 terminal
candidates. A reverse enumeration loops e,f,c,d, derives both intermediate
bases by exact division, then loops a and derives b by a power-of-two test.
Both complete enumerations give exactly one assignment:

```
(a,b,c,d,e,f) = (5,0,0,1,13,0)
B9 = 8161; B13 = 8191; cost = 28.
```

The enumeration is exhaustive only for the specified fixed spine and cost
bound. It is not a search over all addition chains, all graph labellings, or
source optima. Its uniqueness claim is computational, not a Lean theorem.
No timeouts or heuristic choices enter it; seed: none, exact Python integers,
standard library only, Python 3.9.6. The saved forward/reverse experiment took
0.043285 seconds; the integration report records the final-source rerun.

## Construction and mathematical explanation

The source parent pairs in value form are
`(1,1),(2,2),(4,4),(8,1),(9,4),(8,8),(16,13)`.
No Hansen marking exists: the 8+8 step requires 8 as the latest mark, but the
preceding 9+4 step requires the intervening 9 to be marked. Python exhausts
all 64 endpoint-fixed masks; Lean checks all 128 choices of the seven marks,
including both endpoint choices, against the existing existential-summand
`IsHansenFrom` predicate.

The lifted bases are
`[1,3,15,255,8161,8191,65535,536870911]` and their shift caps are
`[1,2,4,8,0,0,13,0]`. Every base has the prescribed source bit count; every
base sum is carry-free. The path through source vertices 1,2,4,8,16,29
uses all maximal outgoing shifts: `1+2+4+8+13=28`. All 36 allocated values
are distinct. Sorting and
independent summand-index replay give exactly 35 additions. The same explicit
summand values are kernel checked using the existing `replay` soundness
and upper-bound theorems.

The repair works because

```
8161 = 2^5*(2^8-1)+1
8161 + 2*(2^4-1) = 2^13-1.
```

Lean also proves the general local identity

```
(2^(b+1)*(2^a-1)+1) + 2*(2^b-1) = 2^(a+b+1)-1.
```

It reuses `mersenne_block_identity`. This identity alone does not give a
general allocation theorem, distinctness or global count. The next concrete
question is its application to the parametric source family recorded in TODO.
